# 怎么评估检索质量（设计文档必答题）

本文说明召回、回答和引用支持分别如何度量，以及这些证据不能证明什么。原始报告保留在 `eval/`，不因后续口径变化改写当时的数字；指标定义与限制以本文为准，历史裁决见 [子 Issue D](子Issue-D-离线评估.md)。检索与判定取舍见 [子 Issue B](子Issue-B-索引管线.md) B-17 与 [子 Issue C](子Issue-C-问答Agent.md) C-6。

## 一、一句话回答

检索质量不是一个数，是三个问题，各自要一把尺子：

| 问题 | 尺子 | 调不调回答模型 | 抓得住的失败 | 抓不住的失败 |
|---|---|---|---|---|
| 正确的那篇资料进候选了吗？ | 离线召回 hit@k（k = 1/3/5/10） | 不调 | 漏召回、被同主题专篇压出前几名 | 判定错、引用错篇、越出片段 |
| 分流是否符合标注？引用中有标注的那篇吗？ | 在线评估：拒答正确率、误拒率、部分覆盖冒充完整、**错源率** | 调 | 库外题没拒、库内题误拒、全部引用错篇 | 答案整体正确性、覆盖完整性；夹带错误来源或只用正确出处装饰答案 |
| 被核对的带引用句是否受支持？ | 逐句引用支持率（同一模型做判官） | 调，增加调用 | 被送审句子的补充、推断与改写 | 无引用句、被跳过的句子及核对失败；判官未经校准，不能作为严格下界 |

再加一组耗时指标：脚本内问答的首段文本与总等待时间，以及检索、判定、生成的分段耗时。hit@k 衡量召回效果，不衡量速度；脚本计时也不等于浏览器端到端延迟，重试与统计边界见下文。

三把尺子分层不是为了指标好看：每一层都有上一层测不出的失败，而 M4 三轮的每一次改动都是被某一层的具体失败题驱动的。

## 二、度量衡先于代码：黄金集怎么出

**M0 先写题再写代码。** 没有题集，任何"检索变好了"都只是感觉。题集设计有四个取舍：

1. **四类题分别检查不同失败。** 直答类 Q（答案在库内，标注出处）、库外类 N（期望拒答）、部分覆盖类 P（有直接相关片段但主体缺失，须声明边界）、改写表达类 R（同义词等表达变化，不表示必须实际执行查询改写）。P 类独立计分源于相似度不能直接代表充分性：Q1 = 0.579，P1 = 0.588 反而更高。当前选择模型做三态判断；这组例子不证明所有阈值方法无效，更不证明只有模型能判定。
2. **每题标一个期望文档，同主题其他文档命中记 miss。** 测的是找到标注文档；没有逐片段标注必要证据，也没有穷举所有有效出处，因此不能等同于找到最佳答案或完整证据。语料 29 篇里 12 篇为同主题干扰项。
3. **N/P 类只展示召回，不进 hit@k 分母。** 离线脚本不执行实际问答分流，不能从候选排名推导拒答是否正确。无候选拒答可由程序直接保证；有候选后的语义判断需要单独验证。
4. **按题集分开解释结果。** v1（30 题）为回归集；v2（12 题）最初留出，后来参与 Q21 修复及策略选择，当前属于开发验证集；v3（19 题）为难例回归集。在线历史报告合跑 v1 + v2 共 42 题，不能当成两次独立验证。文件名中的 `heldout` 保留历史含义，不表示现在仍是未见测试集。

| 集 | 题数 | 为什么要它 | 出题来源 |
|---|---|---|---|
| v1 回归集 | Q16 / N7 / P1 / R6 | M0 度量衡；M2 基线 | 语料的 17 篇出处文档 |
| v2 开发验证集（最初留出） | Q6 / R2 / N3 / P1 | v1 hit@5 饱和，增加原干扰项作为正确答案；已用于定位 Q21 和选择检索策略 | 干扰项作正确出处；N 类增加“主题在库、内容缺失”的边界题 |
| v3 难例集 | Q12 / R3 / P4，每题标难点类型 | 混合检索后 v1/v2 再次饱和；真实使用记录里的失败问法和黄金集的"端正问法"长得不一样 | `scripts/export_history_failures.py` 只读导出本机历史里 REFUSED / PARTIAL 的 10 条（错别字 `checkpiont`、缩写 `FDE`、小写 `git`），人工标注后据此出题；真实问法不入库 |

三集都依赖同一份 29 篇语料，且结果已参与设计决策；同质语料、反复查看题目和依据输出改标都会限制独立性。增加 v3 有助于发现已知难点，但不能替代在冻结实现后，用未参与调试的新语料、新问法和预先标注答案做独立验收。现有报告没有这类独立验收证据。

## 三、在线评估补的三个指标，为什么离线不够

离线召回在 v1 上早已 22/22，但 2026-09-21 第一次在线跑（`eval/answers-baseline-2026-09-21.md`，纯稠密检索）暴露了一件离线永远看不到的事：

**Q21 答错了篇，而现有防线全部放行。** 问"文件写完返回成功、断电为什么还会丢、怎么强制落盘"，标注出处 OS Buffer 短卡逐字含答案措辞，却被 Redis 持久化/过期 Key 两篇专篇的 10 个片段压出前十。判定器看着 Redis 片段判 SUFFICIENT，答案引用 [1][2][3] 全是 Redis——引用格式合法、判定合法、内容也未编造，只是答的不是用户那篇。于是有了三条在线指标（D-1 到 D-3）：

- **错源率** = 已作答且有引用的 Q/R 里，引用片段全部不属于标注出处的比例。它区分两种成因——"标注出处没进候选"（检索层的问题）和"进了候选但没被引用"（生成层的问题），分别对应不同的改进点（D-2）。基线 1/30，成因是前者。
- **拒答正确率 / 误拒率 / P 类冒充完整**：N 类判 NONE 的比例、Q/R 判 NONE 的比例、P 类判 SUFFICIENT 的比例。基线 N 10/10、Q/R 误拒 0、P 1/2。
- **引用支持率**：同一回答模型核对带引用句是否由所引片段支持。复用模型便于固定配置，但生成与核对可能共享偏差；换模型也不能自动消除误判，需要人工标注样本校准。基线 86.9%（192/221）是当时判官对送审句子的结果，抽查见缩写展开、推理补充与改写，不能由此断言没有编造。跨运行句子级结果会变化，单次总量同样不能证明差异显著。

Q21 给出了可定位、可复验的错源样本，因此优先改混合检索，再研究证据压缩。这个顺序是开发优先级，不能推导为“主要错误在检索层，生成层已可靠”。

## 四、三轮实测：数字怎么驱动改动

同一 42 题（v1 + v2）、同一语料、同一回答模型（agnes-3.0-flash）、同一 embedding（bge-m3），每轮只换一处。

### 第一轮：混合检索（B-17，PR #77）

靶子是 Q21。稠密向量按主题相近排序，精确措辞没有额外权重；BM25 恰好补这一点。

| 指标 | dense | hybrid（向量 + BM25 各取前 20，RRF k=60） |
|---|---|---|
| v1 hit@1 / hit@5 | 21/22 / 22/22 | **22/22** / 22/22（R1 补上） |
| v2 hit@1 / hit@5 | 7/8 / 7/8（Q21 前十之外） | 7/8 / **8/8**（Q21 第 4） |
| 在线：标注出处进候选 | 29/30 | **30/30** |
| 在线：错源率 | 1/30 | **0/30**——Q21 核心机制引用 OS Buffer 片段，Redis 相关部分引用 Redis 片段 |
| 拒答正确率 / 误拒 | 10/10 / 0 | 10/10 / 0 |
| Q/R 判 PARTIAL | 6 | 8（Q7、R6 由 SUFFICIENT 变 PARTIAL，各复验两次稳定） |
| 引用支持率 | 86.9% | 85.7%（单次结果，未检验差异显著性） |
| 向量检索段中位 | 9 ms | 7 ms（单次观测，不足以证明混合检索没有额外开销） |

三个取舍：**RRF 不直接加权两类分数**，因为余弦与 BM25 量纲不同，权重需要额外校准；RRF 只融合名次，本项目固定融合常数 60、每通道候选深度 20，并不意味着没有参数；**bm25 单独不能作默认**，v1 退到 19/22@1；**Q7/R6 的代价不调权重去掩盖**——两题 top-1 仍是正确文档，答案只是多了覆盖边界声明，在 30 题上调系数就是过拟合。四种候选规则（dense / RRF / 末位补 1 / 末位补 2）离线对照过，只有 RRF 同时拿到 hit@1 29/30 与 hit@5 30/30。

### 第二轮：判定器标出相关片段，生成只看子集（C-6，PR #78）

靶子不是召回，是"送进生成的证据太多"：基线生成段占完整耗时八成以上，提示中位 1846 字符。判定器已经读过全部候选，让它在同一次调用里多输出"哪些片段支撑判断"，生成与引用只看这些片段、保留原编号。门槛写在前面：支持率不降、错源不升、格式失败率 < 2%、生成耗时与输入字符下降。

中位数采用原始 JSON 的标准 median，展示值按报告取整；偶数样本取中间两值平均。

| 指标 | hybrid | hybrid + relevant |
|---|---|---|
| 送入生成的候选 | 160/160 | **76/160**（32 题全部只送子集，中位 2–3 个） |
| 标注文档的片段被判定器全部排除 | — | **0 题** |
| 生成提示字符数中位数 | 1881 | **1096** |
| 生成调用中位数 | 7780 ms | **5013 ms** |
| 错源 / 拒答正确 / P 类 | 0/30 / 10/10 / 1/2 | 0/30 / 10/10 / 1/2 |
| 引用支持率 | 85.7% | 87.3%（单次结果，未检验差异显著性） |
| 判定调用中位 | 978 ms | 956 ms（跨运行观测，不足以证明额外输出没有代价） |

"标注文档片段被全部排除 = 0 题"说明该样本没有整篇标注来源被筛除，但不证明每个必要片段都保留；仍需结合回答覆盖与引用支持率判断。提示字符数是代码可归因的确定性变化；生成耗时同向下降但第三方接口当日波动大，所以只写"报告中的生成调用中位数下降"，不写百分比承诺。

### 第三轮：难例集 v3 与"不做改写重查"的证据（PR #79）

M4 计划的最后一步是"有界改写重查"，触发条件事先写明：**某集出现 hybrid 仍未进 top-5 的 Q/R 题**。v3 就是为这个条件准备的靶场——错别字、缩写、中英混用、精确术语、专篇压制短卡。

| 策略 | hit@1 | hit@5 | 未到第 1 的题 |
|---|---|---|---|
| dense | 13/15 | 15/15 | Q24（pdflush）第 2、Q31（Socket Buffer 短卡）第 3 |
| bm25 单独 | 14/15 | 15/15 | Q31（Socket Buffer 短卡）第 2 |
| **hybrid（默认）** | **15/15** | **15/15** | — |

错别字题（`volumn`、`seesion`）两个通道都容错；两道新的"专篇压制短卡"在 hybrid 下都是第 1。在线（hybrid + relevant）：Q 12/12、R 3/3 无误拒，错源 0/15，判定器 19 题全部标出子集（95 个候选送入 39 个），首字中位 3.2 s、完整 9.9 s。

同一份 [v3 原始报告](eval/answers-v3-hybrid-2026-09-22.json) 的引用支持率是 **61/77（79.2%）**，有 16 个送审句被判为不支持，另有 19 个无引用句未进入支持率分母。无引用句不一定都是事实断言，但也不能默认正确。v3 与前两轮题集不同，不能把这个差值直接解释为版本退化；它说明命中文档、没有全错出处，仍不等于答案可靠。

**结论：现有三集的 Q/R 在 hybrid top-5 中均命中标注文档，尚无已经验证能由改写重查挽救的样本，因此暂不实现。** 文档命中不保证命中必要片段、集齐多处证据或回答主体正确；新增失败样本也应覆盖这些情况。保留单轮是当前成本与证据下的取舍，不证明多步检索没有价值。

## 五、被实测纠正的两处口径

评估口径不是一次定死的，两处被数据改过，都记在子 Issue D：

- **D-6：词法陷阱题从库外类改为部分覆盖类。** v3 三题观察输出后，按“主题直接相关、主体缺失”的定义改标为 P4–P6，要求说明缺失部分。这种标注修订可以有业务理由，但不是独立盲评；应保留修订依据，并在新题上先标注再运行。N8 或这三题的结果都不足以证明模型普遍分得清 NONE/PARTIAL。
- **D-7：仅整句明确为纯说明时不送核对。** 当前口径 `cited_sentence_support_v2` 只排除整句匹配有限模板的纯说明，例如“以上回答严格基于片段”“无法回答该问题”；匹配前仅去掉引用编号、首尾空白和句末标点。“覆盖边界说明”前缀本身不构成豁免；“基于提供的资料，Redis 默认端口为 9999”“Redis 事务未包含回滚功能”“库中只有这些内容”均含待核对断言。混合事实或不确定句仍送审，模板不尝试穷举自然语言，可能多核对一些纯说明。JSON 的 `summary.faithfulness.metric_version` 与 Markdown 报告均记录口径。

引用支持率为 `supported / (supported + unsupported)`，分母 `checked_sentences` 只包含取得有效判官结果的带引用句；无引用句、明确的纯元话语句、核对失败或输出无效分别展示，不计入该分母。没有有效结果时支持率为空，不记为通过。引用编号合法与语义支持是不同检查；判官可能双向误判，未经人工校准不能作为严格下界。

2026-09 的历史报告保留原始数字与当时口径；旧关键词过滤会漏掉含事实的混合句，不能从旧报告的“未报告不支持”推断这些句子已通过核对。新口径不覆盖或重算旧报告，也不据此推算旧结果被高估的幅度；比较趋势须使用相同口径重新评估。独立标注与判官校准另见 [#93](https://github.com/epoch-fresh-2026/EasyRAG/issues/93)。

标注与过滤规则需要接受和产品代码一样的审查。修改规则后应记录覆盖变化并重新验证，不能只因为得分提高就认为修改正确。

## 六、评估怎么保持诚实

- **隔离**：两个脚本都只用 `sample-knowledge/` 与 `eval/` 的黄金集，在纯 ASCII 临时目录建隔离索引，只 import 各模块 `public`，不读业务 MySQL、不开业务 Chroma、不写历史、不改模型配置。
- **可对照的前提**：比较策略时固定语料、题集、模型、标注与指标版本，记录变更项。重复测量前，逐题翻转和总量差异都只能作为观察，不能未经检验归为噪声或改善。
- **耗时比较**：检索也受缓存、硬件和运行负载影响，模型调用还受接口波动影响。历史基线、hybrid、relevant 报告分别有 3、4、2 道题重试，旧报告的最后一次耗时与最终状态不能代表首次成功率或总等待。当前脚本已记录整题等待和逐次尝试，具体边界见下表；新旧口径不直接比较。
- **报告记录样本数字，不当概率保证**（D-4）；报告与同名 JSON（含候选与完整答案）入库 `eval/`，命令行只记相对路径。
- **脚本自己节流**（D-5）：首跑 42 题里 35 题在判定阶段 80 ms 内被第三方接口拒绝，是逐句核对的密集调用触发限流；评估脚本加停顿、冷却和整题重跑，产品代码的"不自动重试"不变。
- **难例采样**：历史导出默认只选 REFUSED/PARTIAL，会漏掉系统自信答错的 ANSWERED。脚本已有 `--status ANSWERED`，可以单独导出供人工检查；系统状态本身不能作为正确性标注。
- **没测的**：真实用户库上的召回（语料同质，v3 的真实问法只有 10 条）；判官自身的准确率；评估看板与自动调参未做，也不打算做。

### 重试、成功率与计时口径

当前 JSON 的 `summary.retry_accounting_version` 与 Markdown 报告标为 `retry_accounting_v2`。每题从进入问答重试循环计时，到最后一次 `Qa.stream` 尝试结束；包含检索、模型调用和模型网络等待，**不包含**会话创建、后续逐句引用核对、题间停顿、产品 HTTP 入口、历史写库或浏览器渲染。产品问答仍不自动重试。

| 逐题字段 | 含义 |
|---|---|
| `total_ms` | 整题总等待，包含全部失败/成功尝试、实际退避和循环编排 |
| `last_attempt_ms` | 最后一次尝试的耗时 |
| `execution_ms` | 全部尝试耗时之和，不含退避；是墙钟时间，不是 CPU 时间 |
| `backoff_ms` | 实际测得的退避等待之和，包含调度造成的超时等待 |
| `first_text_ms` | 从整题开始到最终尝试出现首段非空文本；最终尝试无文本时为空 |
| `attempt_history` | 每次尝试的状态、失败原因、判定、耗时、相对本次开始的首字时间、分段耗时、模型调用数与后续退避 |
| `stage_ms` | 最后一次尝试的分段耗时；早先尝试保留在 `attempt_history` 中 |
| `model_calls` | 全部问答尝试实际发起的判定/生成调用数，含失败 |
| `support_sentences` / `support_calls` | 送核对的逻辑句子数 / 实际核对调用尝试数，后者含失败和重试 |

`total_ms` 还含少量循环编排耗时，因此不要求与 `execution_ms + backoff_ms` 严格相等。重试时丢弃前次生成文本，整题首字指标取最终尝试；前次已经产生过文本的时刻仍保留在逐次记录里。调用计数统计脚本发起的 `complete/stream`，当前模型 SDK 配置为 `max_retries=0`。

`summary.completion` 分别报告首次与最终技术成功的数量和比例，分母是有尝试记录的题数。正常作答、部分作答和拒答均算技术成功，不代表回答正确或引用获支持。仅有一次失败后重试成功，不能记作首次成功。逐句核对的失败数由引用支持率部分另报。

历史报告保留运行时原始数字：旧 `total_ms` 只表示最后一次尝试，旧 `support_calls` 按核对句子计数。缺失的失败耗时和调用细节不能事后回填；新旧数据须按版本解释，不直接比较，也不从最终成功状态推算首次成功率。

## 八、结论适用范围

报告度量的是指定语料、题集、配置与运行条件下的结果。局部检索题的 hit@k、错源率及引用支持率，不能证明系统能正确回答全库数量、完整清单或全库概览。当前问答没有把数据库统计与完整目录提供给模型；即使引用编号有效，也可能把某篇资料中描述的另一个知识库误当成当前资料库。

这类错误需要单独核对回答对象、统计口径和上下文覆盖，不应用“已有题集无漏召回”作为通过依据。全局问答上下文属于后续设计，本次报告没有评估它。
