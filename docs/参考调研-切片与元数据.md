# 参考调研：切片策略与元数据提取

> 本文保留候选方案和调研依据，不代表全部方案已采用。当前实现采用标题层级切片与混合检索；自动关键词、标签检索和父子切片未启用。现行裁决以 [索引模块](子Issue-B-索引管线.md) 为准，下方“待议/候选”描述属于调研语境。


> 目的：为待议项 A-4（无 frontmatter 用户的结构化过滤如何生效）与 A-5（chunk 结构是否需要调整）准备候选方案，避免全盘自设计。
>
> **可信度标注**：`[已确认]` = 通过检索确认该项目/功能存在；`[待核对]` = 实现细节来自既有知识，落地前需查官方文档或源码验证。本次调研中 github.com、raw.githubusercontent.com、官方文档站均被网络策略拦截，无法读取源码与文档原文，因此细节一律标 `[待核对]`。

---

## 一、切片策略（对应 A-5）

### 1. 标题层级感知切分 —— 我们已采用的方向

| 实现 | 状态 | 说明 |
|---|---|---|
| LangChain `MarkdownHeaderTextSplitter` | `[已确认]` 存在 | 按 `#/##/###` 切分，标题路径写入 chunk metadata |
| LlamaIndex `MarkdownNodeParser` | `[已确认]` 存在 | 同类思路，产出带层级信息的 Node |
| FerrowAI/text-chunker | `[已确认]` 存在 | 自述为「sentence/paragraph/markdown-heading aware, configurable overlap, per-chunk metadata, zero runtime dependencies」 |

**结论**：我们设计的 `heading_path` 与业界主流一致，不是自创。这一点在设计文档里可以直接引用——「按标题层级切分并保留标题路径」是 LangChain 与 LlamaIndex 都提供的一等能力。

`[待核对]` 通用组合用法：先按标题切分，对超长小节再用 `RecursiveCharacterTextSplitter` 二次切分，避免单个 chunk 过大。这是我们 M2 的默认策略候选。

### 2. 字符偏移保留 —— 支撑溯源精度

| 实现 | 状态 | 说明 |
|---|---|---|
| LlamaIndex Node 的 `start_char_idx` / `end_char_idx` | `[待核对]` | Node 自带原文偏移字段，用于回溯原文位置 |
| LangChain `RecursiveCharacterTextSplitter(add_start_index=True)` | `[待核对]` | 开启后 metadata 里带 `start_index` |

**结论**：`char_start / char_end` 也是业界既有做法。但要注意，标题切分器是否同样提供偏移需要落地时验证——若不提供，需要自己在切分后用原文定位补算。这是 A-5 里「切片实现会比一行调用复杂」的具体来源。

### 3. 父子分段（Parent-Child / Small-to-Big）—— M4 的重点候选

| 实现 | 状态 | 说明 |
|---|---|---|
| Dify「父子分段模式」 | `[已确认]` 存在 | 检索到多篇中文详解文章；社区 issue #19105 讨论进一步引入 LLM 语义切分 |
| RAGFlow「子分片策略」 | `[已确认]` 存在 | 官方文档有 `configure_child_chunking_strategy` 页面；issue #7996 为父子块与 overlap 的功能请求 |
| LangChain `ParentDocumentRetriever` | `[待核对]` | 小块检索、返回父块 |
| LlamaIndex `AutoMergingRetriever` | `[待核对]` | 命中多个子块时自动合并回父块 |

**核心思路**：小块（child）做向量检索——语义聚焦、embedding 质量高；大块（parent）喂给 LLM 生成——上下文完整。检索命中 child 后返回其 parent。

**解决的问题**：切太小则上下文断裂（答案被切断，正如黄金集 R2 这类跨段问题），切太大则 embedding 语义被稀释、检索命中率下降。父子分段是这个两难的标准解法。

**对我们的影响**：若 M4 采用，`chunk` 表需要区分层级——加一个 nullable `parent_chunk_id`，或加 `chunk_level` 字段。**这是 A-5 需要现在就决定的一件事：预留字段，还是等采用时再迁移。**

### 4. 上下文增强切片（Contextual Retrieval）

`[待核对]` Anthropic 提出的做法：索引时给每个 chunk 前置一小段「该片段在文档中的位置与上下文」说明，再做 embedding。公开材料称能显著降低检索失败率。代价是每个 chunk 一次 LLM 调用（可用 prompt caching 摊薄成本）。

与 A-4 的自动元数据属于同一类手段——**用索引时的算力换检索时的命中率**。

### 5. RAPTOR（递归摘要成树）

`[已确认]` RAGFlow 的 `parser_config` 中有 `raptor` 相关配置项。思路是把 chunk 递归聚类并逐层摘要，形成树结构，解决「需要综合多篇才能回答」的问题。

**判断：对本项目过度**。我们的规模是几十到几百篇，且黄金集里没有跨多篇综合类题目。记录备查，不列入候选。

## 二、元数据自动提取（对应 A-4）

问题重述：`tags` 只有写 frontmatter 的用户才有值，对其他用户是死功能。要让结构化过滤对所有人生效，元数据必须能自动产出。

### 1. LlamaIndex Metadata Extractors —— 最贴合的现成设计

`[待核对]` LlamaIndex 提供一组索引期抽取器，产出的字段写入 Node metadata，可参与 embedding 或过滤：

| 抽取器 | 产出 | 对我们的价值 |
|---|---|---|
| `TitleExtractor` | 文档标题 | 我们已有降级链，不需要 |
| `KeywordExtractor` | 关键词 | **直接替代 frontmatter 的 tags** |
| `SummaryExtractor` | 摘要（可含相邻块摘要） | 与上下文增强切片同类 |
| `QuestionsAnsweredExtractor` | 「这段能回答哪些问题」 | **最有意思**：对生成的问题做 embedding，缓解「用户问法与原文用词不一致」——正是黄金集需改写类（R1–R7）要打的痛点 |
| `EntityExtractor` | 实体 | 对技术笔记价值一般 |

**结论**：A-4 的答案基本就在这里。`KeywordExtractor` 思路解决「tags 对所有用户生效」，`QuestionsAnsweredExtractor` 思路解决「需改写类命中率」。两者都不要求用户改变习惯。

### 2. 低成本替代：传统关键词抽取

`[待核对]` TF-IDF / TextRank / jieba 关键词抽取：零调用成本、结果确定、可离线、正文更新后重抽也不心疼。缺点是语义弱，同义词覆盖不如 LLM。

### 3. 取舍维度

| 维度 | LLM 抽取 | 传统关键词 |
|---|---|---|
| 质量 | 好 | 一般 |
| 成本 | 每篇一次以上调用 | 零 |
| 确定性 | 同一输入可能不同输出 | 完全确定 |
| 时效性 | 正文改了要重抽（重索引时顺带） | 同样重抽，但无成本顾虑 |

## 三、映射到我们的路线

关键判断：**上面每一项都可以用黄金集验证是否值得，所以不必现在选**。正确顺序是先拿基线，再逐个加、逐个量。

| 阶段 | 做法 | 产出的证据 |
|---|---|---|
| M2 | 最朴素：标题层级切分 + 超长小节二次切分，无自动元数据 | 基线 hit@k 数字 |
| M4 | 逐项加，每项一个 PR，标题带前后数字 | 每项改进的实测收益 |

M4 候选，按预期收益/成本比排序（待实测校正）：

1. **混合检索**（向量 + 关键词 BM25）—— 不需要改数据模型，成本最低
2. **自动关键词抽取**（先传统方法，不够再上 LLM）—— 解决 A-4
3. **父子分段** —— 解决上下文断裂，但要改 `chunk` 表
4. **问题式索引**（QuestionsAnswered 思路）—— 针对需改写类
5. **上下文增强切片** —— 成本最高，最后考虑

**这条清单本身就是设计文档里「检索不准时怎么办」的答案**：不是一句「可以做 rerank」，而是一个带优先级、带成本估计、每项都会被同一套黄金集检验的候选队列。
