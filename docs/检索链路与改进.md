# 检索链路与改进

EasyRAG 当前用一次混合检索取得候选：向量检索负责语义相近，BM25 补充精确措辞，按排名融合后交给问答流程。改进从具体失败题出发，先确认正确证据在哪一层丢失，再决定调整切片、召回、判定或生成。

本文面向首次了解项目的技术评审。阅读后应能解释混合检索的取舍，并根据候选、采用状态和引用定位答非所问的原因。资料与索引的关系见[知识建模与组织](知识建模与组织.md)，指标定义与复现命令见[评估检索质量](评估检索质量.md)。

## 一、当前链路与每层输出

```text
原始问题
  → 问题向量化
  → dense 最多 20 个候选 + BM25 最多 20 个候选
  → 按 chunk ID 融合排名（RRF，常数 60）
  → 返回 top-5，保留真实余弦分数
  → 三态判定与 relevant 筛选
  → 生成或拒答，再校验引用
```

默认 embedding 是 BGE-M3、1,024 维；向量与词法通道使用同一批索引代表片段。向量输入为正文加非空 Markdown 标题路径，BM25 从对应 Chroma 载荷派生。标签不参与过滤或排序，独立的文档标题字段也不会额外拼到每片输入。

每个通道默认取 20 个候选，并非每次都有 40 个不同片段：两个通道可以重叠，实际记录不足或词法未命中时数量会更少。模块请求的 top-k 大于 20 时，候选深度至少达到 top-k；当前问答应用固定使用默认 top-5。

BM25 采用 jieba 搜索粒度分词和少量虚词过滤。`redis-check-aof`、`sync_threshold` 等英文标识符同时保留完整词与拆分词，以兼顾命令全名和局部术语。词法没有匹配时按向量顺序返回；embedding 失败属于技术失败，当前没有切换为纯 BM25 的在线降级流程。

检索模块只决定候选顺序，不决定“这些内容够不够回答”。有候选后仍由问答模块判定覆盖程度，具体见[问答工作流与边界](问答工作流与边界.md)。

## 二、为什么采用排名融合

倒数排名融合（RRF）对一个片段在不同通道中的名次求和，排名从 1 开始：

```text
RRF(chunk) = Σ 1 / (60 + 该片段在通道中的排名)
```

没有出现在某通道的片段，不贡献该通道的项。两边都排在前列会得到较高融合分；并列时保持首次出现的顺序。常数 60 控制不同名次贡献的差距，候选深度 20 控制每个通道的参与范围，两者是当前明确固定的参数。

| 选择 | 解决的问题 | 代价或未解决的问题 |
|---|---|---|
| dense + BM25 | 同时利用语义相近与原文措辞，减少专题长文挤掉短卡 | 增加分词、评分和词法候选余弦补算 |
| 融合名次，不直接加权两种分数 | 余弦和 BM25 的数值量纲不同，不需要校准分数权重 | 丢弃分数间距，排名变化仍会改变后续判定 |
| 返回 top-5 给判定器 | 限定模型阅读量，保留多个可能来源 | 排名靠后的必要证据仍可能遗漏 |
| BM25 随写入全量重建 | 词法语料始终从当前 Chroma 载荷生成 | 当前小规模可接受，扩大语料后需重测写入成本 |

API 的 `score` 保留真实余弦相似度，融合只改变返回顺序。仅由词法召回的片段会补算余弦。因此 rank 1 的 score 可能低于 rank 2；它不是 RRF 得分，也不是答案可信度。

当前没有相似度阈值或交叉编码重排。阈值难以区分“主题相关”和“足以回答主体”；重排则只能调整已经进入输入集合的证据。若目标片段根本没有召回，先给现有候选换顺序不能补回它。

## 三、具体失败：引用合法，仍然答错来源

[v2 的 Q21](eval/golden-set-v2-heldout.md)问文件写入返回成功后为何断电仍会丢失，以及如何强制落盘。标注来源是 OS Buffer 短卡，原文直接写有写回机制与 `fsync` 等调用。

纯向量检索却把 Redis 持久化、过期 Key 等同主题专篇排在前面，短卡未进前十。判定器看到相关资料后判为 SUFFICIENT，生成了格式合法的 Redis 引用。链路没有技术异常，但答案没有引用本题标注的那篇资料。

这个案例区分了三种检查：

- 引用编号校验能确认 `[n]` 指向允许的候选，不能确认候选来源合适。
- 逐句支持核对能判断一句话是否来自所引片段，不能证明它回答了用户所问对象。
- 对照标注来源和候选排名，才发现目标在检索层已被排除。

引入 BM25 后，短卡的原文措辞获得另一个召回入口。RRF 将 Q21 提到第 4，进入默认的 top-5；在线答案开始引用这张短卡解释核心机制。

| 同语料对照 | dense | hybrid | 原始报告 |
|---|---:|---:|---|
| v2 的 Q/R hit@5 | 7/8 | 8/8 | [dense](eval/retrieval-v2-dense-2026-09-22.md)、[hybrid](eval/retrieval-v2-hybrid-2026-09-22.md) |
| Q21 标注来源排名 | 前十未命中 | 第 4 | 同上 |
| v1 + v2 在线错源率 | 1/30 | 0/30 | [在线基线](eval/answers-baseline-2026-09-21.md)、[混合检索](eval/answers-hybrid-2026-09-22.md) |

hit@5 的分母只含有唯一标注来源的直答题 Q 和改述题 R；前五个片段任一个来自该文档就算命中，不先按文档去重。错源率的分母则是已作答且有引用的 Q/R，衡量引用是否全部落在标注来源之外。两者不能互相代替。

混合检索也有代价：既有对照中 Q7、R6 的 top-1 仍是正确来源，判定却从 SUFFICIENT 变为 PARTIAL，回答多了覆盖边界声明。这个结果保留在[评估论述](评估检索质量.md)中，没有针对少量题继续调融合权重将它隐藏。

## 四、检索不准时，先定位再改

当前 trace 保存最终交给判定器的候选及原 rank，并记录 `relevant`。它不包含两个通道各自全部候选和 RRF 中间分数；排查融合原因还需要在隔离评估中分别运行 dense、BM25 和 hybrid 对照。

| 可观察现象 | 先判断什么 | 对应改进与验证 |
|---|---|---|
| 正确内容尚未入库或未完成索引 | 是否存在可用证据 | 修复收录/索引状态，确认当前正文进入索引 |
| 原文有答案，切片未包含完整内容 | 是丢失原文，还是答案跨片 | 核对切片覆盖和容量；用相同题集验证切片改动 |
| 标注来源没有进入 top-5 | 两通道是否都漏，或融合后被挤出 | 对照更深候选与分通道排名，再试召回或融合调整 |
| 来源进入候选，却被 relevant 排除 | 判定器是否漏掉必要证据 | 检查原片段和采用集合，验证筛选后的回答覆盖 |
| relevant 已含答案，正文没用上或越界 | 是生成遗漏、错误归纳还是无依据补充 | 检查实际引用与逐句支持，不把它记成漏召回 |
| 没有足够资料却给出完整结论 | 主题相关是否被误判为主体完整 | 按 NONE/PARTIAL/SUFFICIENT 契约检查判定 |
| 出处缺失、旧正文仍被命中 | 派生索引与业务原文是否一致 | 进入恢复核验，不靠提示词掩盖数据问题 |

例如“pdflush 在哪个内核版本被替代”会命中提到该线程的资料，但语料没有版本信息。提高词法排名不能创造缺失事实；合理结果是说明已有相关内容和未覆盖部分。[v3 难例集的 P4–P6](eval/golden-set-v3-hard.md)专门检查这种术语命中而主体缺失的情况。

每次调整先固定失败题、预期出处或缺失范围，再使用相同语料与配置对照。召回调整看 hit@k，判定调整看误拒和部分覆盖，生成调整看实际引用与支持情况；同时检查回归题和延迟。完整计分方法由[评估检索质量](评估检索质量.md)集中维护。

## 五、为什么目前不增加改写重查

如果原问题的正确来源未进 top-5，改写可能提供新的检索表达；它也增加一次模型调用和检索成本，甚至把具体问题改成另一个问题。当前未启用改写，不把所有 PARTIAL 或 NONE 都当成自动重查信号，因为这些状态也可能准确反映知识缺失。

现有 hybrid 报告中，v1 的 Q/R hit@5 为 22/22、v2 为 8/8、v3 为 15/15；分别见 [v1](eval/retrieval-v1-hybrid-2026-09-22.md)、[v2](eval/retrieval-v2-hybrid-2026-09-22.md)、[v3](eval/retrieval-v3-hybrid-2026-09-22.md)。v3 还覆盖了错别字、缩写、中英混用和专题压制短卡，原问题已经全部命中。

这些样本中没有已证明能由重查挽救的 Q/R 漏召回题，因此当前保留一次检索。重新评估的触发条件是出现 hybrid top-5 仍遗漏标注来源的题；届时先确认错误确在召回，再比较改写前后命中、误改、调用数与延迟。有界重查的方向是初次检索加至多一次改写，尚无已启用的第二轮实现。

## 六、适用范围

三套题集来自同一套 29 篇样例语料，分别用于回归、留出和难例验证。它们需要分开报告；全命中只说明这些问题找到了标注文档，不保证实际用户资料上的召回，也不保证每个必要片段都被保留或答案忠实。

“库里共有多少资料”“完整列出某类内容”“概括整个资料库”还需要数据库统计或完整目录等上下文。当前问答只看局部正文检索结果，尚未接入这些信息源。即使找到一段描述另一个知识库数量的文字，也不能把它当作当前库的事实。

分类树、统计/目录上下文、查询改写重查和工具自主调用均未实现，V2 已延期。后续工作的依据应是新的失败类型和对应验证集，而不是把现有的局部检索命中率扩展成全库问答能力。
