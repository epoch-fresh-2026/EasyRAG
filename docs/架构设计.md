# 架构设计

## 当前架构：FastAPI 模块化单体（2026-09-15）

用户已确认统一为一个 FastAPI 后端，业务模块互不引用，各模块维护自己的实现和数据。当前设计、公开接口、恢复边界和实施检查点以 [FastAPI 模块迁移设计](fastapi-modules.md) 为准。

A 资料管理独占 MySQL；B 检索索引独占 Chroma 与 embedding；C 问答只依赖注入的检索/模型接口；F 回答模型独占本机配置和 SDK。G 负责 HTTP、模块装配、跨模块用例和运行许可。D 离线评估、E Vue 前端作为外部调用方。

后端保留 8080、MySQL 与现有前端契约。迁移实现使用 `rag-service/app/modules/{knowledge,retrieval,qa,answer_models}` 和 `app/application`；Python 业务模块内无 FastAPI、兄弟模块或应用层依赖，G 只能读取 `public.py`。模块内部实现可独立修改，跨模块数据使用明确的快照和端口。

数据库迁移由 A 显式初始化或核验旧 Flyway V2 后接管；G 的 HTTP 与维护 CLI 共用进程锁。恢复会核对资料、切片、向量 ID、归属、正文和元数据，失败时关闭问答，保留资料浏览与模型配置。请求取消、后台任务和停机的资源边界均有测试。

运行方式见 [README](../README.md)，公开字段与状态码见 [API 文档](api.md)，实际停服、备份、接管和回退结果见 [切换记录](../README.md)。必答题"怎么评估检索质量"的正文（黄金集设计、三层指标与 M4 三轮前后数字）见 [评估检索质量](评估检索质量.md)。以下为原 Java + Python 阶段的历史设计，不再作为新模块的依赖约束。

## 历史设计：Java + Python 阶段

> 配套：[总功能文档](总功能文档-Issue.md) 定义产品边界；本文档定义技术拆分。各模块内部实现见子 Issue。

## 一、系统构成

三个进程，两条通信边界。

```
┌──────────────┐   REST    ┌──────────────────┐  内部 HTTP  ┌─────────────────┐
│  E 前端       │ ────────► │  A 知识管理服务    │ ─────────► │  B/C RAG 引擎    │
│  Vue 3 + TS   │ ◄──────── │  Spring Boot      │ ◄───────── │  Python FastAPI  │
└──────────────┘           └────────┬─────────┘            └────────┬────────┘
                                    │                                │
                                 MySQL                        Chroma + BM25
                              （唯一真相源）                   （派生索引，可重建）
```

**Python 不直接暴露给前端，也不读写 MySQL。** 前端的每一个请求都经 Spring Boot。这样"谁能写数据"只有一个答案，出处定位、评估记录、索引状态机都不需要考虑第二个写入者。

## 二、模块划分

| 模块 | 位置 | 作用 | 边界（不做什么） |
|---|---|---|---|
| **A 资料管理** | Spring Boot | 收录/更新/删除资料、内容哈希与变更检测、chunk 落库、索引编排、对前端的全部 REST | 不做切片、不做 embedding、不做检索 |
| **B 索引管线** | Python | 切片、embedding、向量与词法索引的构建与失效 | 不持有业务真相、不读 MySQL、不反向调用 Java |
| **C 问答 Agent** | Python | 检索、查询改写与重查、拒答判定、带引用生成、检索 trace | 不落库、不决定出处的最终展示形态 |
| **D 评估** | 跨栈 | 黄金问答集、跑集（hit@k / 拒答正确率）、结果存储 | 不参与线上问答链路 |
| **E 前端** | Vue 3 | 收录与管理界面、问答界面、检索过程展示 | 不直连 Python、不做业务判断 |

## 四、架构不变量

这四条是硬约束，改动前必须先推翻它们本身。

1. **MySQL 是唯一真相源。** 资料、chunk 文本与元数据、黄金集、评估结果全部在 MySQL，且只有 Spring Boot 写入。
2. **派生索引可重建。** 向量与词法索引按 `chunk_id` 关联 MySQL。删掉 `rag-service/data/` 再重启不丢任何真相，代价只是重建时间。
3. **溯源链路贯穿全程。** `chunk_id` 从索引带到 API 响应，中途不丢。
4. **拒答是一等行为。** 检索质量不足时不进入生成，不编造。

## 五、用示例把模块串起来

### 示例一：收录一篇资料（U1）

```
E  上传 note.md
└► A  存原文 + 算内容哈希 → MySQL document（状态 PENDING）
   └► B  POST /chunk：按标题层级切片，返回片段 + UTF-8 字节偏移
   ◄─┘   （切片是纯计算：不生成 ID、不碰索引）
   └► A  chunk 落库、生成 chunk_id → MySQL chunk（状态 INDEXING）
      └► B  POST /embed：整篇 chunks → 向量 → 写入 Chroma
      ◄──┘
      A  标记 INDEXED
```

**为什么切片要跑一趟 Python 再回 Java 落库**：切片算法在 Python（Java 生态无对等库），但 ID 与数据主权必须在 Java——否则就出现了第二个真相源。代价是多一次往返，换来的是不变量 1 无例外。

### 示例二：问一句话（U4）

```
E  提问
└► A  转发问题
   └► C  检索 → 片段不足则改写重查 → 仍不足则拒答
   ◄─┘   返回：答案 + chunk_id[] + 检索 trace
   A  用 chunk_id 查 MySQL，补出处定位（文档标题、字节偏移）
E  展示：答案 + 可点开的出处 + 检索过程
```

**为什么出处定位由 A 补而不是 C 直接返回**：C 只认识 `chunk_id`，文档标题与路径是业务数据，在 MySQL 里。让 C 去查库会破坏不变量 1。

### 示例三：改了资料再问，答案跟着变（U3）

```
E  重新上传 note.md（内容已改）
└► A  内容哈希比对 → 不一致
   └► A  旧 chunk 失效 → 重新走示例一的切片与 embedding
      └► B  按 document_id 整篇替换索引（先清旧、后写新）
   A  标记 INDEXED
E  再问同一个问题 → 走示例二 → 答案基于新内容
```

**为什么用整篇替换而不是增量更新**：一篇文档改动后，片段边界会整体漂移，逐片段 diff 的复杂度远高于重算，而单篇重算成本很低。简单换正确。

## 六、两个关键取舍

**索引重建走推模式，不是拉模式。** 全量重建由 Java 编排——Java 调 `POST /reset`，再分批调 `/embed`。Python 从不反向调用 Java、不读 MySQL。

代价：Java 要写编排逻辑。收益：Python 侧零外部依赖即可启动，两个服务不会互等；"谁依赖谁"只有一个方向，排查故障时不必考虑环形调用。这条边界有可执行验收——Python 源码里 grep 不到 Java 地址，依赖里没有数据库驱动。

**跨语言定位口径统一为 UTF-8 字节偏移。** Python 的字符串下标是 Unicode 码点，Java / JS 是 UTF-16 码元。只要正文出现非 BMP 字符（emoji），两侧算出的偏移就会静默错位，出处高亮指向错误位置。两侧各有一份契约测试，跑同一份共享用例数据。

## 七、技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | —— |
| A 模块 | Spring Boot 4.1 + MySQL 8 | JdbcTemplate 而非 JPA，不过早固化领域模型 |
| B/C 模块 | Python + FastAPI | 切片与检索生态在 Python |
| 向量库 | Chroma | 原生元数据过滤与按 `document_id` 删除；几百篇规模下 FAISS 的性能优势无意义，而元数据能力缺失是实痛 |
| 模型 | 可配置 | provider / model / dim 三元组，不绑定厂商 |

选型本身不是加分项，够用即可。真正的设计在边界划分和上面两个取舍。
